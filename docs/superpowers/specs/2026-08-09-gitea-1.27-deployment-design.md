# Gitea 1.27 Deployment Design

> [!NOTE]
> This is a historical deployment design. The [2026-08-14 Backblaze migration](2026-08-14-gitea-backblaze-storage-migration-design.md) supersedes its current object-storage provider details. IDrive e2 references below describe the original deployment; other architectural decisions remain historical context.

## Objective

Deploy Gitea 1.27.1 on the Debian 13 host
`gitea.lab.canhdinh.com` using Ansible. Gitea must use the existing PostgreSQL
18 service, iDrive e2 object storage, the prepared SMTP credentials, and a
trusted certificate issued by the existing `lego` role.

Success means a repeatable, idempotent deployment installs a signature-verified
Gitea binary, provisions its database, serves Git and the web application only
over built-in HTTPS on port 443, disables Gitea SSH, creates the initial
administrator, and passes configuration and deployed health checks without
using deprecated Gitea options.

## Approved Decisions

- Deploy the current stable Gitea release, 1.27.1, as a pinned binary.
- Add inventory host `gitea` at `gitea.lab.canhdinh.com`.
- Use one `gitea.yaml` playbook with an ordered PostgreSQL play followed by a
  Gitea host play.
- Use a reusable `gitea` role for the application host.
- Create a dedicated `gitea` PostgreSQL role and database on the existing
  PostgreSQL 18 host.
- Connect to PostgreSQL with `SSL_MODE = verify-full`.
- Serve Gitea directly with its built-in HTTPS server on port 443.
- Use lego certificates and no reverse proxy.
- Disable Gitea's SSH transport; leave host administrative SSH unchanged.
- Use the prepared iDrive e2 S3-compatible storage and SMTP secrets.
- Enable registration with mandatory email confirmation and require
  authentication to view Gitea.
- Create initial administrator `gitea-admin` with email
  `gitea-admin@canhdinh.com` from a SOPS-encrypted generated password.
- Document the local Git repository backup gap without adding backup automation.

## Architecture

### Inventory And Playbook

The inventory gains a `gitea` host under the existing `lab` group:

```yaml
lab:
  hosts:
    gitea:
      ansible_host: gitea.lab.canhdinh.com
```

The `gitea.yaml` playbook contains two plays.

The first play targets `postgres` and uses `community.postgresql` modules to
create the login role and UTF-8 database. Secret-bearing database tasks use
`no_log`. This play does not alter the PostgreSQL server configuration because
the existing role already enforces TLS, SCRAM-SHA-256, and access from the lab
and Tailscale networks.

The second play targets `gitea` with privilege escalation. It runs the new
`gitea` role and then the existing `lego` role. The Gitea role installs the
binary and runtime dependencies, creates the service account and paths, renders
configuration, starts the service with a temporary certificate when needed,
and bootstraps the administrator. The lego role then obtains the trusted
certificate and replaces the temporary identity through its deploy hook.

### Gitea Role

The role owns:

- Gitea version, paths, hostname, HTTPS port, database, storage, mail, and
  administrator defaults.
- Runtime package installation, including Git and certificate tooling.
- The dedicated `git` system account and `/var/lib/gitea` working directory.
- Signature verification and atomic installation of `/usr/local/bin/gitea`.
- `/etc/gitea/app.ini` and the managed TLS destination.
- The `gitea.service` systemd unit and restart/reload handler.
- Initial database migration through normal Gitea startup.
- Idempotent initial administrator creation.
- Input validation and template-focused tests.

Application data, local repositories, indexers, generated OAuth signing keys,
and queues live below `/var/lib/gitea`. Configuration and TLS identity live
below `/etc/gitea`.

## Binary Installation And Upgrade Lifecycle

The role pins `gitea_version` to `1.27.1` and maps Ansible architectures to the
official Gitea release artifact names. A version change is explicit and
reviewable rather than dynamically resolving `latest` on every deployment.

Before installation, Ansible downloads the binary and detached signature to a
staging path. It verifies the signature with GPG using the official Gitea
release key fingerprint `7C9E68152594688862D62AF62D9AE806EC1592E2`. Only a
successful verification permits atomic installation as
`/usr/local/bin/gitea` with root ownership and mode `0755`.

The final binary path never contains a version number because Gitea repository
hooks embed that path. A changed binary notifies a controlled systemd restart.
The README requires a consistent Gitea backup before future version changes.

## HTTPS And Certificate Lifecycle

Gitea's built-in server listens directly on port 443. The systemd unit follows
the official Gitea service model and grants the unprivileged `git` process only
`CAP_NET_BIND_SERVICE` so it can bind the privileged port.

The role seeds its managed TLS paths from Debian's snake-oil certificate only
when no certificate exists. This permits the service and database migration to
start before the first ACME issuance. The temporary certificate is replaced
before deployment completes and is not the accepted final identity.

The `lego` role requests an EC certificate for
`gitea.lab.canhdinh.com` through the existing Cloudflare DNS challenge. Its
deploy hook:

1. Validates that the issued certificate is currently valid.
2. Verifies that the certificate and private key public keys match.
3. Stages both files in `/etc/gitea/tls` with `root:git` ownership and
   restrictive permissions.
4. Atomically replaces the active certificate and key.
5. Gracefully reloads Gitea through systemd so new connections use the renewed
   identity.

Gitea uses TLS 1.2 or newer. It does not start an HTTP redirect listener, so no
Gitea plaintext HTTP port is exposed.

## Gitea Configuration

The role renders only settings required for this deployment. It does not copy
the complete example configuration.

### Server

The `[server]` section sets:

- `PROTOCOL = https`
- `DOMAIN = gitea.lab.canhdinh.com`
- `ROOT_URL = https://gitea.lab.canhdinh.com/`
- `PUBLIC_URL_DETECTION = never`
- `HTTP_ADDR = 0.0.0.0`
- `HTTP_PORT = 443`
- `DISABLE_SSH = true`
- `START_SSH_SERVER = false`
- `SSH_CREATE_AUTHORIZED_KEYS_FILE = false`
- `SSH_CREATE_AUTHORIZED_PRINCIPALS_FILE = false`
- `CERT_FILE` and `KEY_FILE` under `/etc/gitea/tls`
- `SSL_MIN_VERSION = TLSv1.2`
- `LFS_START_SERVER = true`
- `LFS_ALLOW_PURE_SSH = false`
- `LFS_JWT_SECRET` from SOPS
- `ALLOW_GRACEFUL_RESTARTS = true`

The `[repository]` section keeps HTTP Git enabled and sets
`GO_GET_CLONE_URL_PROTOCOL = https`. Disabling Gitea SSH does not disable the
host SSH daemon used for Ansible administration.

### Database

The `[database]` section uses:

- `DB_TYPE = postgres`
- `HOST = postgres.lab.canhdinh.com:5432`
- `NAME = gitea`
- `USER = gitea`
- `PASSWD` from SOPS
- `SSL_MODE = verify-full`
- `LOG_SQL = false`

The database is owned by the PostgreSQL login role `gitea` and created with
UTF-8 encoding. The server's existing
`password_encryption = scram-sha-256` setting ensures the new login role uses
SCRAM authentication.

### Object Storage

One `[storage]` section supplies the default for attachments, LFS, avatars,
repository avatars, repository archives, packages, Actions logs, and Actions
artifacts:

- `STORAGE_TYPE = minio`
- `MINIO_ENDPOINT` from `gitea_s3_endpoint`
- `MINIO_ACCESS_KEY_ID` from `gitea_s3_access_key`
- `MINIO_SECRET_ACCESS_KEY` from `gitea_s3_secret_key`
- `MINIO_BUCKET` from `gitea_s3_bucket`
- `MINIO_LOCATION` from `gitea_s3_region`
- `MINIO_USE_SSL = true`
- `MINIO_INSECURE_SKIP_VERIFY = false`
- `MINIO_CHECKSUM_ALGORITHM = default`
- `MINIO_BUCKET_LOOKUP_TYPE = auto`

The settings target iDrive e2's S3-compatible API. Git repository object data
is not part of Gitea's configurable object-storage classes and remains on the
Gitea host.

### Mail And Sessions

The `[mailer]` section enables email and uses current Gitea 1.27 keys:

- `SMTP_ADDR` from `gitea_smtp_host`
- `SMTP_PORT` from `gitea_smtp_port`
- `FROM` from `gitea_smtp_from`
- `USER` from `gitea_smtp_user`
- `PASSWD` from `gitea_smtp_password`
- `FORCE_TRUST_SERVER_CERT = false`

Gitea infers the documented SMTP protocol from the configured port. The
configuration does not use legacy `HOST`, `MAILER_TYPE`, or `IS_TLS_ENABLED`
mailer options.

The `[session]` section uses `PROVIDER = db`, `COOKIE_SECURE = true`, and
`SAME_SITE = lax`. Database-backed sessions survive application restarts
without introducing another service.

### Access And Security

The `[security]` section sets `INSTALL_LOCK = true` and reads stable
`SECRET_KEY` and `INTERNAL_TOKEN` values from SOPS. The `[oauth2]` section also
reads its stable `JWT_SECRET` from SOPS. Local repository imports and custom
Git hooks remain disabled. Reverse-proxy authentication and proxy header trust
are not enabled.

The `[service]` section sets:

- `DISABLE_REGISTRATION = false`
- `SHOW_REGISTRATION_BUTTON = true`
- `REGISTER_EMAIL_CONFIRM = true`
- `REQUIRE_SIGNIN_VIEW = true`
- `ENABLE_NOTIFY_MAIL = true`

Console logging is retained so systemd journal owns collection and rotation.
The configuration avoids deprecated `LFS_CONTENT_PATH`, picture storage
options, and deprecated mail queue settings.

## Secret Management

The existing SOPS file retains the prepared object-storage and mail values. The
implementation adds these encrypted keys:

- `gitea_database_password`
- `gitea_secret_key`
- `gitea_internal_token`
- `gitea_lfs_jwt_secret`
- `gitea_oauth2_jwt_secret`
- `gitea_admin_password`

General-purpose values are independently generated with `openssl rand -hex
32`. The LFS and OAuth2 JWT secrets are exactly 32 random bytes encoded as
43-character raw URL-safe base64 values, as required by Gitea 1.27. Values are
inserted with `sops set`; plaintext is not written to temporary tracked files
or printed in command output.

The rendered `app.ini` is owned by `root:git`, uses mode `0640`, and is rendered
with `no_log`. Secret-bearing database and administrator tasks also use
`no_log`.

## Administrator Bootstrap

After Gitea has started and migrated its database, Ansible lists existing
administrators using the version-matched Gitea CLI. If `gitea-admin` is absent,
it creates the user with:

- Username `gitea-admin`.
- Email `gitea-admin@canhdinh.com`.
- Password from `gitea_admin_password`.
- Administrator privileges.
- Mandatory password change on first login.

Subsequent playbook runs do not reset the password or alter the existing user.

## Failure Handling

- Role inputs and required SOPS values are validated before host mutation.
- Database creation runs before application deployment and fails without
  logging the database password.
- A failed GPG verification leaves the active Gitea binary untouched.
- An invalid rendered service or configuration prevents restart.
- Certificate deployment leaves the active identity untouched if validation or
  staging fails.
- systemd records startup and runtime failures and restarts unexpected exits.
- Administrator creation runs only after a healthy service startup and remains
  idempotent.

## Verification

Repository-level checks include:

```sh
cd ansible
ansible-playbook --syntax-check gitea.yaml
ansible-playbook --syntax-check verify-gitea.yaml
ansible-playbook roles/gitea/tests/render-config.yml
ansible-lint gitea.yaml verify-gitea.yaml roles/gitea
```

The render test validates required sections, safe quoting, the systemd unit,
and certificate hook. It also asserts that the output omits known deprecated
options used by older Gitea deployments.

The deployed `verify-gitea.yaml` playbook confirms:

- `/usr/local/bin/gitea --version` reports 1.27.1.
- `gitea.service` is enabled and active.
- Gitea listens on HTTPS port 443 and does not expose its default port 3000.
- Gitea's built-in SSH server is disabled and no Gitea SSH listener exists.
- HTTPS presents a trusted, unexpired certificate valid for
  `gitea.lab.canhdinh.com`.
- The install page is locked, registration requires email confirmation, and
  anonymous repository views require authentication.
- `gitea-admin` exists with administrator privileges.
- `gitea doctor check --default` succeeds.
- A second deployment run reports no changes.

The README documents dependency installation, deployment, verification,
idempotence rerun, first login, useful systemd and journal commands, and the
requirement to take a consistent backup before upgrades.

## Backup Boundary

The existing PostgreSQL pgBackRest jobs cover Gitea's relational data. iDrive
e2 stores configured binary assets such as attachments and LFS objects. Neither
mechanism backs up local Git repositories, generated OAuth signing keys,
indexers, or queues below `/var/lib/gitea`.

Gitea's official backup guidance requires stopping the service for a fully
consistent backup across its database and mutable files. Automated off-host
backup of the Gitea host is intentionally deferred. Until that work is added,
the deployment does not tolerate loss of the Gitea host and its local storage.

improves validation without changing the approved ownership boundaries.

## Out Of Scope

- A reverse proxy or external TLS terminator.
- Gitea SSH access, built-in or through the host SSH daemon.
- Registration without email confirmation or external identity providers.
- Gitea Actions runner deployment.
- Redis, external indexers, or horizontal Gitea scaling.
- Host firewall management.
- Automated local or off-host Git repository backups.
- Automatic unpinned upgrades to newly published Gitea versions.

## Acceptance Criteria

- One playbook command converges PostgreSQL and a clean Debian 13 Gitea host.
- Gitea 1.27.1 is installed only after its release signature is verified.
- Gitea is reachable at `https://gitea.lab.canhdinh.com/` with a trusted lego
  certificate and no reverse proxy.
- Gitea offers Git over HTTPS and does not offer Git over SSH.
- PostgreSQL, iDrive e2, and SMTP use the prepared or generated SOPS secrets
  without plaintext leakage.
- New registrations require email confirmation before account activation.
- The initial `gitea-admin` account exists and must change its generated
  password at first login.
- Render, syntax, lint, deployed health, TLS, CLI doctor, and idempotence checks
  pass.
- The deployed configuration contains no deprecated Gitea options.
- Documentation states the remaining local repository backup risk.
